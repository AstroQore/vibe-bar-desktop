# Localization

Desktop does not author user-facing strings. Both clients read one catalog,
[`AstroQore/vibe-bar-i18n`](https://github.com/AstroQore/vibe-bar-i18n), whose
`AGENTS.md` is the contract: a key is an identifier, placeholders are named,
`en.json` is the only file where a string is written, and the glossary of
proper nouns is data that CI enforces rather than a convention. Read that
file before adding a key; this one only says what Desktop does with it.

The catalog ships two lanes from one repository, the way `agent-session-kit`
does: a Swift package the native app pins, and an npm package this client
pins. Same keys, same placeholders, same translations — which is the point.
A string that reads one way here and another way there is the failure this
arrangement exists to prevent.

## What Desktop does with it

```jsonc
"@astroqore/vibe-bar-i18n": "0.1.0"
```

```ts
import { t } from "@astroqore/vibe-bar-i18n";

t("common.retry");
t("quota.resetsIn", { days: 3, hours: 18 });
```

Keys are a union type and placeholders are typed, so a typo or a missing
argument is a compile error rather than a `%@` in someone's menu bar. The
version is pinned exactly, as the kit is: a catalog that moves under a
release is a release whose screenshots lie.

Nothing here reads `catalog/*.json`. The generated module is the API, and
that is what lets the catalog change shape without touching a call site.

## The language the app is in

The picker is a Desktop setting, not a shared one — the native app follows
macOS's own language list and an in-app override sets its bundle, which has
no equivalent here. Absent a choice, Desktop follows the system language and
falls back to English for a locale the catalog does not carry.

Whatever that resolves to is the app's locale, and it is the only one: the
catalog lookup and every date, number and calendar in the interface read the
same value. A WebView default that disagrees with the picker is how a UI ends
up half in one language.

Simplified Chinese is the first translation. English is the source.

## What has to change here before a key can replace a string

Three patterns in this repository are not translatable as they stand. They
are not bugs today — English tolerates them — and each becomes one when a
second language arrives. They are listed so the work is visible, not so it is
done all at once: each is fixed as the surface it belongs to is localized.

**Plurals chosen in code.** Sixteen sites pick a word by comparing a count:

```ts
shown === 1 ? "1 session" : `${shown} sessions`
`${view.providers} provider${view.providers === 1 ? "" : "s"}`
```

Simplified Chinese has one plural form, Polish has four, and neither is
expressible as a ternary. Each becomes one ICU key:

```json
"session.count": {
  "value": "{count, plural, one {# session} other {# sessions}}",
  "placeholders": { "count": "int" }
}
```

**Sentences built by concatenation.** A joined sentence survives only while
every language shares English's word order:

```ts
`${listed} now ${names.length === 1 ? "holds" : "hold"} the other copy's value.`
`${used}% used · ${left}% left${describeReset(cycle)}`
```

Each becomes a single key with the values as placeholders. Where a clause is
optional, that is two keys, not a key plus an appended fragment.

**Numbers and dates formatted for one language.** This is the largest of the
three and the easiest to miss, because none of it looks like a string:

- `toLocaleString("en-US")` in seven places, pinning the grouping separator to
  English inside sentences that will not be.
- Hand-written month and weekday tables — `SHORT_MONTHS` in
  `popover/format.ts`, `MONTHS`/`MONTHS_LONG` in `workbench/resets/model.ts`,
  `MONTHS`/`WEEKDAYS`/`WEEKDAYS_LONG` in `workbench/usage/model.ts` — with the
  day and month assembled in English order.
- `toLocaleDateString(undefined, …)`, which follows the WebView's locale. That
  is the OS language, not the app's, so the moment the picker disagrees with
  the system a date is in one language and the sentence around it in another.
- Number formatters written by hand, in four modules:
  `compactTokens`, `formatMicroUSD`, `compactUSD` and `formatPercent` in
  `workbench/usage/model.ts`; `formatCost` and `formatTokens` in
  `popover/format.ts`; `formatPerMillion` in `workbench/settings/model.ts`.
  Every one builds its output with `toFixed` and literal `.`, `k`, `M`, `B`,
  `$` and `%`, and none calls a locale API — which is what makes them
  invisible to a search for one, and what would put English numbers inside a
  Chinese sentence for any locale that groups with spaces or decimates with a
  comma. `Intl.NumberFormat` does all of them, compact notation and currency
  included.
- Dates rendered at the WebView's default locale in `SettingsPage.tsx`, which
  is the same OS-versus-app mismatch as above.

Formatting is Desktop's job, not the catalog's — the catalog receives the
formatted string or the raw number — which is precisely why every formatter
has to be given the app's selected locale rather than assuming one. The
month and weekday tables become `Intl.DateTimeFormat` with that locale; the
number formatters take it as an argument. A calendar's column order follows
the locale's first day of the week, too.

Concretely: one resolved locale, threaded from the language setting into every
formatter, and no module-level constant that names a month.

## What does not become a key

Log lines, MCP tool names and their schemas, JSON keys, file paths, account
ids, provider raw values, and anything else a machine parses. Localizing a
machine-readable string breaks the machine, and several of these are
byte-compatible with the native app's storage on purpose.

**Stable names are not the same thing as generic labels.** A SubProvider is
called Codex in every language; a bucket titled `Weekly`, a filter chip
reading `All`, and a grouping row called `Other` are English words that
happen to arrive through the same pipe. The rule is the id, not the source:
an identifier that must stay byte-compatible with the native app's storage
is contract-bound and never a key, while the text drawn from it is a key
whenever that text is a word rather than a name. `All` and `Other` are in
`docs/contracts/quota-naming-v1.json`; `Weekly`, `5 Hours` and `30 Days`
come out of the adapters. All of them are display text.

Names on the two axes come from different places, and neither is the
catalog. On the quota axis, company, SubProvider and bucket names come from
`naming.rs` and the shared design-token contract. On the usage axis, harness
labels come from `sessions.rs::harness_display_name` and
`cost.rs::harness_name`, and model names come from the events themselves —
whatever the harness recorded. All of them appear in the catalog's glossary
only so a translator cannot translate them.

The distinction matters during adoption: a label that is data flowing out of
a session file is never a key, while the synthetic text around it — an
"Unknown model" fallback, a "no local scanner" note — is.
